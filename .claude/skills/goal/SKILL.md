# goal — 목표를 검증 가능하게

## 목적

"성능을 개선하자"는 목표가 아니다. **끝났는지 판정할 수 없기 때문이다.**
이 스킬은 소원을 판정 가능한 문장으로 바꾼다.

## 좋은 목표의 조건

목표 하나가 아래를 전부 만족해야 한다.

| 조건 | 질문 |
|---|---|
| 측정 가능 | 숫자나 참/거짓으로 판정되나? |
| 현재값 있음 | 지금 값이 얼마인지 아나? 모르면 그것부터 재는 게 첫 목표다. |
| 기한 있음 | 언제까지인가? |
| 통제 가능 | 우리 행동으로 움직이나, 아니면 남의 사정인가? |
| 대리지표 아님 | 이 숫자가 올라가면 정말 원하는 게 좋아지나? |

## 변환 예시

| 소원 | 목표 |
|---|---|
| 앱을 빠르게 | 목록 화면 첫 렌더 p95를 1200ms → 400ms 이하로, 이번 주까지 |
| 코드를 깔끔하게 | `src/api` 순환 의존 7건 → 0건, 다음 배포 전까지 |
| 테스트를 늘리자 | 결제 모듈 분기 커버리지 41% → 80%, 2주 내 |
| 사용자를 늘리자 | 주간 재방문 사용자 320 → 500명, 10월 말까지 |

## 진행 순서

1. **원하는 결과를 한 문장으로 받는다.** ("무엇이 좋아지길 바라나요?")
2. **현재값을 먼저 잰다.** 모르면 측정이 첫 번째 작업이다. 기준선 없는 목표는 나중에 성공을 자칭하게 만든다.
3. **목표값과 기한을 정한다.** 근거를 붙인다 — 왜 400ms인가? (사용자가 체감하는 임계? 경쟁 제품? 그냥 감?)
4. **측정 방법을 못 박는다.** 누가, 어떤 명령/도구로, 어떤 조건에서 재는가. 재현 가능해야 한다.
5. **깨지면 안 되는 것(guardrail)을 정한다.** 목표를 달성하면서 망가뜨리면 안 되는 지표. 이게 없으면 목표는 편법으로 달성된다.
6. **범위 밖을 명시한다.**

## 산출물

```markdown
## 목표: <이름>

**결과 문장**: <지표>를 <현재값>에서 <목표값>으로, <기한>까지.

**왜 이 값인가**: ...

**측정 방법**: <명령/쿼리/도구>, <조건>, <측정자>

**기준선**: <현재값> (측정일: YYYY-MM-DD, 측정 방법 위와 동일)

**깨지면 안 되는 것**
- <지표>가 <값> 아래로 내려가지 않는다
- 기존 테스트 전부 통과

**범위 밖**
- ...

**완료 판정**
- [ ] 측정값이 목표값 이상/이하
- [ ] guardrail 전부 유지
- [ ] 측정이 재현됨 (2회 이상)
```

## 하지 말 것

- 기준선 없이 목표값만 정하는 것
- 여러 목표를 동시에 세우는 것 — **한 번에 하나.** 목표가 셋이면 우선순위를 매겨 하나만 남기고 나머지는 대기열에 둔다.
- 측정 방법을 "나중에 정하자"로 미루는 것
- 통제 불가능한 지표를 목표로 삼는 것 (예: "경쟁사보다 빠르게")

## 연계
