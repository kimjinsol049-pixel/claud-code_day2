# SDD — Spec-Driven Development

## 핵심

코드가 아니라 **명세가 진실의 원본**이다.
구현이 명세와 다르면 둘 중 하나가 틀린 것이고, 어느 쪽인지 정한 뒤에 고친다.
명세 없이 짠 코드는 리뷰할 기준이 없다. "동작은 하는데 이게 맞나?"를 판정할 수 없다.

## 단계

### 1. SPEC — 명세 작성 (코드 금지)

`docs/spec/<기능이름>.md`에 아래를 쓴다. **이 단계에서 소스 파일을 건드리지 않는다.**

```markdown
# <기능 이름>

## 목적
<누가 무엇을 할 수 있게 되는가. 한 문단.>

## 범위
### 포함
- ...
### 제외
- ...

## 동작 명세
### <시나리오 이름>
- 전제: ...
- 입력: ...
- 결과: ...

## 인터페이스
<함수 시그니처 / API 엔드포인트 / CLI 옵션 / 데이터 스키마. 타입까지 적는다.>

## 오류 처리
| 상황 | 동작 | 사용자에게 보이는 것 |
|---|---|---|

## 불변식
<항상 참이어야 하는 것. 예: 잔액은 음수가 될 수 없다.>

## 수용 기준 (Acceptance)
- [ ] 검증 가능한 문장으로. 각 항목이 하나의 테스트가 된다.

## 미결정
- <정하지 못한 것과, 그래서 어떤 기본값으로 갔는지>
```

명세가 흐릿하면 [interview](../interview/SKILL.md)로 돌아가 채운다.

### 2. REVIEW — 명세 검수

구현 전에 명세를 사용자에게 보여주고 승인받는다.
승인 전에 [grillme](../grillme/SKILL.md)로 한 번 턴다. 명세 단계의 구멍은 코드 단계의 100분의 1 비용으로 메워진다.

체크:
- 수용 기준 하나하나가 테스트로 옮겨지는가?
- 오류 경로가 정상 경로만큼 적혀 있는가?
- 인터페이스가 실제 타입까지 확정되었는가?

### 3. PLAN — 작업 분해

명세를 커밋 단위로 쪼갠다. 각 조각은 **혼자서도 통과하는 상태**여야 한다.

```markdown
1. <조각> — 관련 수용 기준: #1, #2 — 파일: src/...
2. ...
```

### 4. BUILD — 구현

- 한 번에 한 조각.
- 각 조각을 끝낼 때 어떤 수용 기준을 채웠는지 명시한다.
- 구현 중 명세와 어긋나는 걸 발견하면 **코드를 몰래 바꾸지 말고 멈춘다.** 명세를 고칠지 코드를 고칠지 사용자에게 묻고, 명세를 고쳤으면 문서를 실제로 수정한다.
- 테스트를 먼저 쓰는 편이 나으면 [tdd](../tdd/SKILL.md)로 전환한다. SDD와 TDD는 충돌하지 않는다 — 명세가 위, 테스트가 아래다.

### 5. VERIFY — 대조

수용 기준을 하나씩 짚으며 확인한다. 실제로 실행해서 확인하고, 실행 결과를 붙인다.

```markdown
| 수용 기준 | 상태 | 근거 |
|---|---|---|
| #1 ... | ✅ | tests/x_test.py::test_a 통과 |
| #2 ... | ❌ | 미구현 — 이유 |
```

통과하지 못한 항목은 숨기지 않고 그대로 보고한다.

### 6. SYNC — 명세 갱신

구현 중 바뀐 결정을 명세에 반영해서 커밋한다. 문서와 코드가 어긋난 채로 끝내지 않는다.

## 규칙

- **명세 없이 구현 시작 금지.** 사용자가 급하다고 하면 최소 명세(목적·인터페이스·수용 기준)만이라도 쓴다.
- **명세는 코드와 같은 커밋에 들어간다.** 나중에 쓰겠다는 문서는 안 써진다.
- **"명세에 없는 기능"은 추가하지 않는다.** 필요해 보이면 명세에 제안하고 승인받는다.
- 명세 파일이 500줄을 넘으면 기능을 쪼갤 때가 된 것이다.
