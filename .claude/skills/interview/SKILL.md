# Interview — 요구사항 인터뷰

## 목적

사용자는 자기가 원하는 걸 다 말하지 않는다. 말할 수 있는 것만 말한다.
이 스킬은 **추측으로 코드를 짜기 전에** 빠진 조각을 질문으로 채운다.

## 원칙

1. **한 번에 한 덩어리씩 묻는다.** 질문 10개를 한꺼번에 던지지 않는다. 3~4개씩, 대답을 보고 다음을 정한다.
2. **답을 이미 알 수 있는 건 묻지 않는다.** 코드베이스·파일·git 이력을 먼저 읽고, 거기서 확인 가능한 건 질문 목록에서 뺀다.
3. **선택지를 제시한다.** "어떻게 할까요?"보다 "A / B / C 중 무엇에 가깝나요?"가 훨씬 빠른 답을 얻는다. 추천안이 있으면 맨 앞에 놓고 이유를 한 줄로 붙인다.
4. **모른다는 답도 유효하다.** 사용자가 "모르겠다"고 하면 기본값을 정해서 제안하고, 가정으로 기록한 뒤 넘어간다. 인터뷰가 취조가 되면 안 된다.
5. **최대 3라운드.** 그 이상 물으면 사용자가 지친다. 남은 불확실성은 "가정"으로 문서에 남기고 진행한다.

## 진행 순서

### 0단계 — 사전 조사
질문을 만들기 전에 먼저 읽는다: README, CLAUDE.md, 관련 소스, 기존 유사 기능.
"이미 있는 걸 다시 묻는" 질문은 신뢰를 깎는다.

### 1단계 — 무엇을/왜 (What & Why)
- 이걸로 **누가** 무엇을 할 수 있게 되나?
- 지금은 그 사람이 **어떻게** 하고 있나? (현재의 불편)
- 이게 없으면 무슨 일이 생기나? (안 만들어도 되는지 확인)

### 2단계 — 경계 (Scope)
- 반드시 되어야 하는 것 (must)
- 있으면 좋은 것 (nice)
- **이번엔 안 하는 것** (out) ← 이 항목이 제일 중요하다. 반드시 명시적으로 받아낸다.

### 3단계 — 구체 (Concrete)
- 성공했을 때 화면/출력이 어떻게 생겼나? 예시 하나만 보여달라.
- 실패·예외 상황엔 어떻게 되어야 하나?
- 데이터는 어디서 오고 어디에 남나?
- 제약: 기한, 성능, 기존 코드와의 호환, 쓸 수 있는 라이브러리

## 산출물

인터뷰가 끝나면 아래 형식으로 **요약해서 사용자에게 확인받는다.**

```markdown
## 요구사항 정리: <이름>

**한 줄 정의**: <누가> <무엇을> 할 수 있게 한다.

### 이번에 하는 것
- [ ] ...

### 이번에 하지 않는 것
- ...

### 동작 예시
입력: ...
출력: ...

### 예외 처리
| 상황 | 동작 |
|---|---|

### 가정 (확인 못 받고 정한 것)
- ...

### 열린 질문
- ...
```

확인이 끝나면 이 문서를 그대로 `docs/spec/<이름>.md`에 저장할지 물어보고,
설계·구현으로 넘어갈 땐 [sdd](../sdd/SKILL.md), 테스트부터 짤 땐 [tdd](../tdd/SKILL.md)로 이어간다.

## 하지 말 것

- 인터뷰 중에 코드를 짜기 시작하는 것
- "알겠습니다, 그럼 이렇게 하겠습니다" 하고 확인 없이 넘어가는 것
- 사용자가 이미 명확하게 말한 걸 다시 확인하는 것
