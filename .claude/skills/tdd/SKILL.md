# TDD — Test-Driven Development

## 핵심 순환

```
RED    실패하는 테스트를 쓴다 → 실행해서 실패를 확인한다
GREEN  통과시키는 가장 단순한 코드를 쓴다 → 실행해서 통과를 확인한다
BLUE   테스트를 초록으로 둔 채 구조를 정리한다 → 다시 실행한다
```

한 바퀴는 작아야 한다. 한 바퀴에 테스트 하나, 몇 분.

## 절대 규칙

1. **테스트가 실패하는 걸 눈으로 본 적 없으면 그 테스트를 믿지 않는다.**
   구현부터 짜고 테스트를 나중에 붙이면, 그 테스트는 자기가 아무것도 검증 안 해도 통과한다.
   먼저 실행해서 빨간 걸 확인하고, 실패 메시지가 **원하는 이유로** 실패하는지도 본다.
   (import 오류로 실패한 건 RED가 아니라 그냥 고장이다.)

2. **테스트를 통과시키려고 테스트를 고치지 않는다.**
   테스트가 틀렸다고 판단되면 왜 틀렸는지 먼저 말하고 고친다. 조용히 기대값을 바꾸는 건 금지다.

3. **GREEN 단계에서는 최소한만 짠다.**
   "어차피 나중에 필요할 것 같아서" 미리 짜지 않는다. 다음 테스트가 그걸 요구할 때 짠다.

4. **리팩터링은 초록일 때만.**
   빨간 상태에서 구조를 바꾸면 무엇 때문에 깨졌는지 알 수 없다.

5. **실행 결과를 그대로 보고한다.**
   "통과했습니다"가 아니라 실제 출력. 실패가 남아 있으면 남아 있다고 말한다.

## 테스트 작성 순서

한 기능에 대해 이 순서로 테스트를 늘려간다.

1. **가장 단순한 정상 경로** 하나
2. **경계값** — 0, 1, 빈 값, 최대값
3. **오류 경로** — 잘못된 입력, 없는 리소스, 권한 없음
4. **불변식** — 항상 참이어야 하는 것
5. **회귀** — 실제로 발생한 버그마다 하나씩

## 버그를 고칠 때

순서를 바꾸지 않는다.

1. 버그를 **재현하는 테스트**를 먼저 쓴다.
2. 실행해서 실패를 확인한다. ← 이게 버그를 정확히 이해했다는 증거다.
3. 고친다.
4. 통과를 확인한다.
5. 그 테스트를 남긴다. 같은 버그가 다시 오면 여기서 잡힌다.

재현 테스트 없이 고친 버그는 고쳐졌는지 알 수 없다.

## 좋은 테스트

- **이름이 문장이다**: `test_잔액이_부족하면_출금이_거부된다`
- **한 테스트가 한 가지를 주장한다**
- **준비 / 실행 / 검증**이 눈으로 구분된다
- **순서에 의존하지 않는다** — 혼자 돌려도 통과한다
- **결정적이다** — 시간·랜덤·네트워크는 고정하거나 격리한다
- **구현이 아니라 동작을 본다** — 내부 함수 호출 횟수를 세는 테스트는 리팩터링 때마다 깨진다

## 무엇을 모킹하나

| 대상 | 모킹? |
|---|---|
| 네트워크, 외부 API | 한다 |
| 현재 시각, 랜덤 | 한다 (주입 가능하게) |
| 파일 시스템 | 임시 디렉터리 사용, 모킹보다 낫다 |
| 내가 짠 순수 함수 | 하지 않는다 |
| DB | 통합 테스트에선 실물(또는 컨테이너), 단위 테스트에선 경계에서 자른다 |

모킹이 많아진다는 건 설계가 외부에 너무 붙어 있다는 신호다.

## 진행 보고 형식

각 순환마다:

```
RED   test_<이름> 추가 → 실패 확인
      AssertionError: expected 400, got None
GREEN <파일>:<함수> 구현 → 통과
      3 passed in 0.12s
BLUE  <무엇을 정리했는지> → 3 passed
```

## 시작 전 확인

- 테스트 러너와 실행 명령이 무엇인가? (기존 테스트 파일을 먼저 읽어 관례를 따른다)
- 테스트 파일 위치와 이름 규칙은?
- 기존 테스트가 지금 전부 통과하는가? ← 시작 전에 한 번 돌린다. 이미 깨진 게 있으면 그것부터 사용자에게 알린다.

- 완료 기준이 흐릿하면 [goal](../goal/SKILL.md).
